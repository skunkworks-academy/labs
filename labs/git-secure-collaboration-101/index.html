LAB-DEV-101 · Secure software collaboration

Git, GitHub and secure collaboration - make every change reviewable, attributable and recoverable.

A branch is a safe place to change code; a commit is a meaningful record; a pull request is a reviewable conversation; and a protected default branch is a team control. Together, these practices help a team ship better work without turning speed into untracked risk.

Module 1

Use a branch and focused commits to make intent recoverable.

Good Git collaboration starts before a command. Link the change to a user need or issue; create a focused branch; make small commits that explain why a coherent change exists; and keep unrelated formatting or refactors out of the same change when possible. This reduces review burden and makes reversion or investigation easier.

  • 1
    Define the change: describe the problem, acceptance criteria and any user, security or operational impact.
  • 2
    Branch deliberately: create an isolated branch named for the change; it is not a substitute for a review or test plan.
  • 3
    Commit meaningfully: record a focused unit of work with a message that explains the outcome rather than only a generic label.
  • 4
    Prepare the pull request: compare the branch against its target and describe scope, validation and risks.

Module 2

Use a pull request to make quality evidence visible.

A pull request is more than a button to merge. It should state the user outcome, files and behaviours changed, validation performed, known limitations, operational/security considerations and a safe rollback route when risk merits one. Reviewers should evaluate the change against intent and evidence, not simply approve a familiar contributor.

Fictional pull request

Improve keyboard focus indicators in the learner dashboard.

Review simulation

Good pull-request evidence

  • What: Visible keyboard focus treatment added to dashboard controls.
  • Why: Keyboard users could not reliably identify the active control.
  • Validation: Page-head check, keyboard traversal and relevant automated checks.
  • Risk: CSS change could affect contrast or responsive layout.
  • Rollback: Revert the single focused commit if a regression appears.

Reviewer questions

  • Does the diff match the stated problem?
  • Are tests/validation relevant and reproducible?
  • Did the author accidentally add secrets or unrelated files?
  • Are user, security and operational impacts understood?

Module 3

Guard the default branch and treat secrets as incidents, not configuration.

A branch protection rule or ruleset can require a review or passing checks before changes merge into a protected branch. It is a delivery control, not a substitute for secure code, testing or incident response. Secret scanning can help detect known credential patterns, but prevention still requires keeping secrets out of code, using approved secret stores and rotating/revoking exposed values promptly.

Repository control design

Set a safe default for the fictional Academy portal repository.

No rule is changed
  • 1
    Protect main: require pull requests, relevant passing checks and an appropriate review policy for changes to the default branch.
  • 2
    Restrict bypass: define who can bypass rules, when and how those exceptional actions are logged and reviewed.
  • 3
    Handle secrets safely: use approved secret management, do not commit credentials and rotate/revoke any value that was exposed.
  • 4
    Keep delivery observable: retain change history, check results and review decisions so incidents can be investigated and corrected.

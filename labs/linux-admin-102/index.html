Module 1

Model file access as a deliberate decision.

A long permission string means little until you know who owns the object, what group is intended to operate it and whether everyone else should have any access.

Owner

The first permission triplet belongs to the file owner.

For a protected configuration, an administrative owner often controls changes. The correct owner depends on the approved operating model.

Group

The second triplet serves a defined operational group.

Use a group when approved support or service accounts need access without making the file broadly accessible.

Other

The final triplet applies to everyone else.

World-readable or world-writable access is rarely the default for application secrets or service configuration.

rwx

Read, write and execute are separate. A file and a directory have different execution semantics.

640

Illustrative: owner read/write, group read, no access for other. It must match the approved use case.

Ownership

Mode alone is insufficient. Pair an intentional user and group with the smallest required permission set.

Module 2

Resolve a shared-service permission request.

The developer needs the running service to read a configuration file. The request is not an instruction to make the file writable by every account.

Simulated terminal evidence

Identify the least-privilege design goal.

No shell access
ops@app-api-02:~$ ls -l /srv/academy-api/config/app.env
-rw------- 1 root root 486 Aug 02 08:14 /srv/academy-api/config/app.env
ops@app-api-02:~$ id academy-api
uid=1024(academy-api) gid=2050(appops) groups=2050(appops)
# Service must read the file. Only approved operations staff should maintain it.

Decision constraints

  • Do not expose secrets through broad “other” permissions.
  • Do not give a runtime account write access just because it needs to read.
  • Use the approved service group and change-control process.

Module 3

Triage a service without destroying the useful context.

A restart might become necessary, but it should not be the first reflex. Read the manager state, preserve relevant logs and follow the authorised path.

Simulated service record

Turn state and logs into a safe next action.

Fictional incident
ops@app-api-02:~$ systemctl status academy-api.service
● academy-api.service - Academy API
   Loaded: loaded; enabled
   Active: failed (Result: exit-code) since 09:14:26
   Process: 8821 ExecStart=/usr/local/bin/academy-api (code=exited, status=1)
ops@app-api-02:~$ journalctl -u academy-api.service --since "09:10"
09:14:26 academy-api[8821]: configuration validation failed: required value unavailable
09:14:26 systemd[1]: academy-api.service: Failed with result 'exit-code'.
# Do not infer the cause or change configuration from this small excerpt alone.

Evidence first

  • Record the unit state and timestamp.
  • Keep the relevant journal excerpt with the incident ticket.
  • Check the approved runbook and ownership before a restart or configuration change.

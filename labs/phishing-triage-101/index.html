Module 1

Build the safe first-pass habit.

Header analysis is useful only when it is paired with controlled handling. The first objective is not to prove a global attribution; it is to preserve the message and give the right team a usable report.

Do preserve

The message, headers, recipient context, time and any user-reported interaction. Use the organisation's approved reporting route.

Do not “confirm” by clicking

Opening a link or attachment can create harm, trigger tracking or alter the evidence. A learner does not need to reproduce an incident.

Do read authentication results

SPF, DKIM and DMARC add evidence. Consider their alignment and the delivery path alongside the message claim.

Do escalate a confirmed interaction

A click, credential submission or attachment execution changes the incident path and requires the approved security response.

Three-line triage note: scope and claim; evidence observed; recommended next action. This turns the report into something a service desk or security analyst can act on.

Module 2

Read a header as a set of clues.

The display name and subject set a story. The following fictional header summary helps you evaluate whether the mail path and authentication evidence support that story.

Synthetic email fixture

Document what the header supports - and what it does not.

No live message
From: Skunkworks Academy Finance <finance@skunkworksacademy.training>
Subject: Action required: payroll profile review
Return-Path: <notices@training-notice.example>
Authentication-Results: mx.training.example;
  spf=fail smtp.mailfrom=training-notice.example;
  dkim=none;
  dmarc=fail header.from=skunkworksacademy.training
Received: from relay.training.example (192.0.2.18)
Body claim: “Review your profile using the secure portal link below.”
Lab note: No link is provided; all identifiers are fictional training values.

Evidence reading guide

  • A display name and From header are not proof of the sender's identity.
  • The return path differs from the visible From domain in this fixture.
  • SPF fail, no DKIM signature and DMARC fail are relevant signals that should be retained in the report.
  • These signals support a cautious disposition; they do not let a learner make a criminal attribution.

Report-ready facts

  • Message subject and time received.
  • Visible From and return path.
  • Authentication result summary.
  • Whether the recipient interacted.

Module 3

Choose the safe disposition and escalation boundary.

What the recipient did matters. A message that is only reported follows one path; a confirmed click, credential entry or attachment execution needs incident escalation.

Case update

The recipient has not clicked, replied or opened an attachment.

No interaction reported
  • 1
    Report: use the organisation's approved report-phishing action or security channel.
  • 2
    Preserve: keep the original message and header evidence available to the authorised reviewer.
  • 3
    Inform: advise the recipient not to click, reply, forward externally or open any attachment.
  • 4
    Escalate if interaction emerges: follow the incident-response playbook if a user reports a click, credential entry or execution.
